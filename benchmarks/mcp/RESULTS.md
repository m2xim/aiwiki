# MCP baseline — 21.10.2026

28 синтетических документов + 5 встроенных статей; 3 новых пространства, 12 поисковых запросов, 7 задач чтения. По 20 повторов после прогрева. Сервер Go/SQLite, loopback, один Windows-хост. Приложение не изменялось; домашний сервер не участвовал в замерах.

## Поиск и необходимость дочитывания

На 11 размеченных положительных запросах macro Recall@5 = Recall@10 = 95.45%, MRR@10 = 0.9545. Единственный отрицательный запрос вернул пустую выдачу. Это не процент правильных ответов агента; 20 повторов одного запроса не создают 20 независимых задач.

В s03 первым оказался нерелевантный документ; оба ожидаемых источника были в top-5. В s11 отсутствовал один из двух ожидаемых источников даже в top-10 (английский handover-template для русского перефразирования). В 6 из 12 запросов сработал ANY fallback. Метки релевантности — авторские суждения для этого корпуса, а не полный эталон промышленной базы.

В 4 из 7 задач чтения буквальный ответ уже присутствовал в поисковом сниппете. Сценарий всё равно принудительно читал источник: сравнение показывает цену выбранного маршрута, а не доказывает необходимость каждого чтения. Нельзя объявлять C оптимальной автономной стратегией: её якорь заранее получен в setup.

Медиана локального search RTT 7.921 мс, p95 13.288 мс на смешанной серии запросов. Это не модельная задержка, WAN latency, нагрузочный тест или гарантия для большой базы.

## Пилот реального агента

Модель claude-sonnet-5-5, effort low, 2.1.301 (Claude Code). Две заранее выбранные задачи r02/r06, две политики чтения, два повтора: 8 отдельных сессий; завершено 8, инфраструктурных сбоев 0. Буквальный ответ с правильным источником и поддержкой в tool-ответах получен в 7/8. Правильный ответ вместе с предписанным маршрутом чтения — 5/8. Эти метрики различаются: ответ из сниппета не доказывает чтение нужного раздела.

Входные токены провайдера включают uncached input + cache creation + cache read; выходные отдельно. Это суммарный usage всей CLI-задачи с повторным контекстом, не proxy токены отдельных payload. Разбиение по кэшу и моделям сохранено в JSON. Provider-reported cost — справочная оценка CLI, не счёт.

Для r02 обе политики дали правильный ответ с соблюдением маршрута в обоих повторах. Сумма input + output провайдера (`totalTokens`) была 38 835 и 38 866 токенов для полного чтения, 36 384 и 36 459 для частичного: снижение около 6.2–6.3%, а не 57.5% из таблицы payload. Повторяемый контекст, дополнительные вызовы и клиентская обвязка существенно меняют результат.

Для r06 оба full-прогона нарушили предписанную политику: в одном модель перешла на чтение разделов, в другом ответила cannot_find. В финальных ответах она сообщила, что полный текст не поместился в ответ инструмента / был сохранён в файл, который она не могла прочитать. Это наблюдение о данном клиенте, не измерение предела контекста модели и не ошибка HTTP сервера. Сравнивать их меньший usage с успешным partial как доказательство эффективности full нельзя.

В обоих outline-прогонах r06 модель сначала выбрала огромный раздел «Рабочие заметки». В одном затем прочитала нужный раздел, в другом нашла ответ уточнённым поиском, но нужный раздел не прочитала. Это показывает разрыв между дешёвым маршрутом сценарного оракула и реальным выбором раздела агентом.

Важная слабость r06: вопрос говорит «в крупном разделе», хотя эталонный раздел занимает 2672 символа, а соседний — около 87 тысяч. Эта неоднозначность могла направить модель к «Рабочим заметкам». Вопрос не изменялся после просмотра результатов; пилот не доказывает, что ошибка вызвана только интерфейсом. Следующий модельный эксперимент должен заранее зафиксировать более ясную формулировку в новой версии корпуса.

Оценщик был исправлен после прогона: наличие правильного якоря в оглавлении больше не считается чтением соответствующего раздела. Одни и те же 8 сохранённых трасс переоценены без новых модельных вызовов; первоначальные 6/8 стали 5/8 по маршруту, при 7/8 правильных ответах. Причина, SHA исходных результатов и версия оценщика сохранены в JSON. Хеш исполнявшегося pilot-runner заранее не записывался; хеш опубликованного исправленного оценщика не выдаётся за хеш исходного исполнения.

CLI работает из отдельного временного каталога, имеет только тестовый read-only MCP. Для full-политики anchor=null допустим; для outline фиксируется использование оглавления перед разделом. Допустимые capability probes (GET 405 и server/discover -32601) сохранены отдельно. Предварительный smoke с ошибками оценщика исключён из этих восьми сессий и сохранён локально.

Две задачи и два повтора не позволяют доказать общее улучшение качества агента. Политики требуют чтения даже при достаточном сниппете. Не смешивать этот пилот с измерениями сценарного оракула; не выводить общий процент экономии из пула разных задач.

## Решение по следующим улучшениям

1. Сохранить частичные чтения и правки: выигрыш payload подтверждён в сценарии с оракулом. В пилоте агента r02 дал около 6% по суммарным provider tokens; для r06 чистое парное сравнение не состоялось из-за нарушений маршрута.
2. Приоритетно прототипировать ограниченное порционное чтение внутри длинного раздела с revision и явным продолжением. Якорь сам по себе не ограничивает объём.
3. Сравнить поиск по разделам с прямым адресом и ограничением выдачи, чтобы убрать обязательное оглавление и лишние кандидаты. Проводить сравнение на том же корпусе с отдельным change/version.
4. Гибридный/векторный поиск проверять отдельно на перефразировании и межъязычных задачах; текущие данные не доказывают необходимость pgvector. Стоимость повторного запроса или перевода запроса тоже должна быть базой сравнения.
5. Эти задачи не проверяют многошаговый граф. Оснований внедрять граф или менять HTTP-транспорт по этому прогону нет.

Ни корпоративные права, ни производственный масштаб, ни устойчивые ID разделов здесь не реализованы. Числа относятся только к опубликованному корпусу и указанным версиям. Повторение на PostgreSQL с ACL необходимо после появления корпоративного ядра.
