# Развёртывание

AI Wiki не имеет встроенной авторизации: любой, кто достиг порта, может читать и изменять данные. Разворачивайте её только в доверенной сети, за VPN или за reverse proxy с аутентификацией. См. [SECURITY.md](../SECURITY.md).

## Локально (loopback)

```sh
docker compose up -d --build
```

`compose.yaml` публикует `127.0.0.1:8090` и хранит данные в `./data`.

При прямом `docker run` указывайте `-p 127.0.0.1:8090:8090`.
Внутри контейнера сервер слушает все интерфейсы; `-p 8090:8090` публикует
неавторизованный сервис на всех интерфейсах хоста.

## Сервер в доверенной сети

`compose.server.yaml` настраивается переменными окружения (например, файлом `.env` рядом с ним, не добавляйте его в репозиторий):

| Переменная | По умолчанию | Назначение |
| --- | --- | --- |
| `AIWIKI_BIND_ADDR` | `127.0.0.1` | адрес хоста, на котором публикуется порт |
| `AIWIKI_PORT` | `8090` | порт хоста |
| `AIWIKI_ALLOWED_ORIGIN` | `http://127.0.0.1:8090` | единственный дополнительный браузерный origin (схема, хост, порт, без пути) |
| `AIWIKI_DATA_DIR` | `./data` | каталог данных на хосте (SQLite, история, комментарии, `files/`) |

Значения должны быть согласованы. Пример для адреса `192.0.2.10`:

```sh
AIWIKI_BIND_ADDR=192.0.2.10
AIWIKI_ALLOWED_ORIGIN=http://192.0.2.10:8090
```

Если изменили `AIWIKI_PORT`, измените и порт в `AIWIKI_ALLOWED_ORIGIN`. Запросы браузера с других origin отклоняются; это не заменяет аутентификацию, поскольку клиенты без заголовка `Origin` (curl, агенты) не проходят проверку браузерного origin.

Для любого запроса сервер проверяет `Host`: разрешены loopback и хост с портом
из `AIWIKI_ALLOWED_ORIGIN`. Поэтому настройте эту переменную и для удалённых
REST/MCP-клиентов. Reverse proxy должен передавать соответствующий `Host`;
`X-Forwarded-Host` сервером не учитывается. Используйте точный браузерный origin
в нижнем регистре, без завершающего `/` и без явного стандартного порта 80/443.

На reverse proxy разрешайте только настроенное публичное имя и сохраняйте
исходный Host клиента вместе с нестандартным портом (например, в nginx
`proxy_set_header Host $http_host` с проверенным `server_name` и отказом
для неизвестных имён). Не переписывайте любой входящий Host в loopback-адрес
backend: это включает локальные исключения CORS для внешних запросов.

Запуск и обновление после получения новых исходников:

```sh
docker compose -p aiwiki -f compose.server.yaml up -d --build
```

Контейнер перезапускается автоматически (`unless-stopped`).

Состояние и логи:

```sh
docker compose -p aiwiki -f compose.server.yaml ps
docker compose -p aiwiki -f compose.server.yaml logs --tail=100 wiki
```

## Резервная копия

Остановка нужна для согласованной копии SQLite и файлов. Укажите свой каталог данных вместо `./data`:

```sh
docker compose -p aiwiki -f compose.server.yaml stop wiki
sudo tar -czf "backup-$(date +%Y%m%d-%H%M%S).tar.gz" -C ./data .
docker compose -p aiwiki -f compose.server.yaml start wiki
```

Храните копии вне каталога данных и вне репозитория. Проверяйте восстановление: запустите копию с `-data` на другом порту.

Контейнер может создавать файлы от root с правами `0600`; для чтения всей копии
могут понадобиться права администратора. В примере выше используется Linux `sudo`.

## Безопасное обновление

1. Остановите сервис и сделайте резервную копию (выше).
2. Дополнительно сохраните прежний образ: `docker tag aiwiki:local aiwiki:before-update`.
3. Соберите и запустите новую версию, проверьте `GET /api/health`.
4. Для сравнения данных выгрузите `GET /api/export` до и после обновления и сравните JSON после разбора.
5. Для отката верните прежний образ и, при необходимости, данные из копии.

## Заметки

- Образ собирается из `Dockerfile` (Node 22 для фронтенда, Go 1.25 для сервера); внешняя модель не нужна.
- Не распаковывайте старую копию поверх текущей базы без остановки сервиса.
- Не публикуйте каталог данных и резервные копии: в них весь ваш контент.
